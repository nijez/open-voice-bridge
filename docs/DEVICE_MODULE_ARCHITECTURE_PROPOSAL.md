# Open Voice Bridge 设备模块架构提案

状态：REVISE（Claude Opus 4.8 对抗性审查后）
任务：XRBM-038

## 1. 用户体验契约

应用把“当前可用设备”和“项目支持目录”分成两个入口：

- **设备工作区**：只显示当前在本机上被可靠匹配、或本次运行中刚断线的适配设备。
- **支持设备**：始终可以打开的完整目录，列出所有内置设备模块、支持平台、连接方式、实现状态和简要设置说明；未匹配设备不会占用主工作区。

状态规则：

1. 零匹配：显示简洁空状态、“重新扫描”和“查看支持设备”。
2. 单匹配：直接进入该设备工作区，不再要求用户手动选择产品型号。
3. 多匹配：显示设备卡片选择器；每个实例按稳定系统身份区分，不只看展示名称。
4. 运行中断线：保留当前卡片并标为“已断开”，允许重连或忘记；不在用户操作过程中突然消失。
5. 重新启动且设备仍不存在：主工作区不再显示该设备，但可在“最近使用”和“支持设备”中找到说明。
6. 权限未知或被拒绝：显示“需要权限才能检测”，不能等同于“设备不存在”。

应用不得根据模糊品牌词、相似名称或“已经配对”单独判定设备可用。匹配必须由模块声明的精确身份和至少一条当前可用传输共同成立。

## 2. 核心对象

### DeviceDescriptor

语言无关的静态资料：设备 ID、厂商、型号、平台支持状态、传输、能力、文档和资源键。继续由 `device-profiles/*.json` 与 schema 管理。

### DeviceDetector

平台专属只读探测器。输出候选实例、匹配证据、可用传输、权限阻断和置信状态；不建立长时语音或按键会话。

### DeviceAdapter

一个已选设备实例的运行会话。负责连接、断线、协议状态、语音帧、逻辑按键边沿和设备状态；不能直接绘制界面或注入平台按键。

### DevicePresentation

设备专属展示资料：实物图、按键热点、状态字段、设置区块以及能力解释。它读取统一状态，不拥有 BLE、HID 或音频资源。

### DeviceModule

注册单元，组合上述对象：

```text
DeviceModule
├── descriptor
├── detectorFactory(platform)
├── adapterFactory(instance, platform)
├── presentation
├── defaultMappings(platform)
└── settingsNamespace
```

### DeviceModuleRegistry

启动时加载内置模块，提供目录查询、按平台过滤、并行探测和按 ID 创建适配器。第一阶段使用编译期内置注册，不加载任意第三方动态代码。

## 3. 能力驱动界面

主界面不再判断 `if RC003 / else DJI`，而根据模块能力组合通用区块：

| 能力 | 通用界面 |
| --- | --- |
| `voice-capture` | 输入源、音频状态、隐私说明 |
| `press-to-talk` | 按住/松开状态与触发设置 |
| `button-input` | 实物图、可用按键和事件状态 |
| `host-key-mapping` | 动作映射、默认值和恢复默认 |
| `gain-control` | 增益设置 |
| `device-status` | 电量、连接与固件可见状态 |

设备可以添加少量专属区块，但必须封装在自己的 presentation 内，不能向公共 `SettingsView` 增加产品名称分支。

实物图只负责识别和交互。没有可靠主机事件证据的实体键可以显示说明，但必须标记为不可映射，不能伪造动作能力。

## 4. 生命周期与资源仲裁

- 探测器可并行运行，但只做短时或低成本观察。
- 只有用户当前激活、且传输可用的实例可以创建运行适配器。
- 切换设备前，协调器必须先停止旧适配器、释放按键、结束音频流和撤销回调，再启动新适配器。
- 同时发现多个语音设备时不得自动抢占系统默认麦克风，也不得在录音中自动切换。
- 迟到回调必须携带实例与会话代次，不能污染新会话。
- 一个模块崩溃或不兼容时应失败关闭该模块，不影响设备目录与其他模块。

## 5. 设置隔离与迁移

设置键使用 `devices.<device-id>.<platform>.*` 命名空间。实例级配置再增加稳定实例 ID。公共设置只保存主题、日志级别等真正跨设备选项。

RC003 现有 UserDefaults 先通过一次显式迁移写入 `devices.xiaomi-rc003.macos.*`，迁移成功前保留只读回退；不能因为改架构丢失用户已有映射。

## 6. 首批模块

### Xiaomi RC003

- 探测：精确蓝牙名称与 HID VID/PID，BLE GATT 与 HID 分别报告证据。
- 适配：BLE ATVV 语音、HID 按键、Fn 映射、桥接暂停和 BlackHole 输出。
- 展示：现有实物图、13 键热点和完整动作映射。

### DJI Mic 2

- 探测：当前平台实际暴露的 CoreAudio/Windows 录音端点；仅蓝牙已配对不算可用。
- 适配：系统音频输入会话；不复用 RC003 ATVV/HID 逻辑。
- 展示：设备图、录音输入状态和实体控制边界。没有可靠 HID 事件的按键只解释用途，不显示可编辑映射。

## 7. 跨平台边界

JSON profile、能力名称、逻辑事件与测试向量跨平台共享；Swift、Windows 实现和未来 Linux 后端分别实现 detector/adapter/platform action。第一阶段不为了“代码统一”强制引入新的跨语言运行时。

新增设备的目标交付结构为：

```text
device-profiles/<device-id>.json
devices/<device-id>/assets/
platforms/macos/devices/<device-id>/
platforms/windows/devices/<device-id>/
platforms/linux/devices/<device-id>/
tests/device-contracts/<device-id>/
```

## 8. 非目标与升级门

- 当前不开放任意第三方动态插件。
- 当前不保证所有设备都有按键映射页。
- profile 本身不是驱动，不能仅添加 JSON 就宣称支持。
- 第三个设备接入前，公共 UI 中不得再出现新的产品名条件分支。
- 只有出现可信的外部模块生态需求，并解决签名、版本兼容、权限与崩溃隔离后，才评估进程外插件。

## 9. 待审查问题

1. “只展示已匹配设备”是否会把权限失败误导成未支持或未连接？
2. 断线保留卡片与重启后隐藏之间是否足够可预测？
3. capability-driven UI 是否会退化成难维护的动态表单？
4. 模块边界能否避免 RC003 的双传输逻辑泄漏到 DJI？
5. 多设备同时存在时，资源仲裁和实例身份是否完整？
6. 内置注册制是否足够支持未来十几种设备与三个平台？
7. 现有设置迁移、权限身份和应用 Bundle ID 是否有遗漏风险？

## 10. 对抗性审查后的强制修订方向

以下项目在进入实现前必须写入下一版架构契约：

1. 设备身份拆成 `advertised` 与 `verified` 两级。RC003 可以先以精确广播候选出现在设备工作区，但只有建立会话并确认协议/传输后才解锁完整功能；不能假装 RC003 与免费的系统音频枚举具有相同探测成本。
2. 发现负责决定“列表里出现什么”，用户选择负责决定“当前切换到什么”。单匹配可以默认聚焦，但不能在活跃语音、HID 或系统映射会话中自动切换适配器。
3. 保留现有手动选择作为多匹配选择器，并定义持久化选择优先级；自动发现不能静默覆盖用户选择。
4. `device-profiles/*.json` 必须先成为 macOS 与 Windows 真正加载的运行时资料源，并建立共享名称匹配测试向量；在此之前不得宣称跨平台目录统一。
5. 当前阶段明确只支持单活跃适配器；同型号多实例和实例级独立配置降级为后续目标，不在首轮承诺。
6. 设备切换 teardown 必须把 F5→Fn 恢复等可失败系统副作用纳入状态机。恢复失败时停止切换并显示可恢复错误，不能静默继续。
7. 设置迁移必须逐键列明归属并双读回退。现有 RC003 的映射、设备 UUID、双击开关、本机 Fn、增益和输出设备均先归入 RC003/macOS 命名空间。
8. 能力驱动 UI 先做薄层：RC003 保留专属块，DJI 复用输入源、音频状态和隐私等真正通用块；第三个设备到来前不做全面动态表单。

修订后的阶段顺序固定为：运行时读取设备目录 → registry 薄封装 → 只发现不自动切换 → 设置命名空间迁移 → 最后抽离 RC003 adapter。每一步都必须保留可关闭的回退路径，并重新通过 RC003 真机门。
